# SPEC：多声源射线追踪的安全性能修复

Status: ready-for-agent

## Problem Statement

多声源仿真会重复承担接收器分配、对象池创建、追踪、滤波和等待成本，但目前的日志无法分离这些阶段，尚无证据确定主要瓶颈。原审计还将若干会破坏声学结果、数据所有权或收敛的建议描述成低风险优化。

已确认的问题包括：对象池重复创建与不安全发布、方向直方图重复分配 Energy、滤波入口的完成／异常契约不清、单频带 RAD 累加竞争、收敛循环长期保留历史任务，以及 Rhino 等待流程中的同步停顿和二次轮询。用户需要降低这些可避免的成本，同时保留现有声学模型和结果可解释性。

本 SPEC 只规定后续代码修改；当前文档状态不表示代码已实现或性能已验证。事实与源码证据见 [修订后的审计](audit.md)，下文沿用其 #1–#10 编号。

## Solution

先建立可重复基线，再分小批实施正确性修复、重复工作删除和等待流程修复。保持声源级串行、现有主接收器累加方式、频带选择、散射模型和收敛阈值；保留现有公开入口签名及结果文件格式。

本期交付包括：

- 每源阶段计时及一份基线／修改后对照报告。
- 安全、幂等的对象池初始化，方向直方图不再重复分配 Energy。
- 明确同步完成且能向调用方传播失败的串行滤波入口。
- 三类 RAD 的可靠并发累加和有效样本边界。
- 只保留本轮追踪任务、每轮完整等待后再检查收敛。
- 不阻塞 Rhino UI、对已完成阶段不额外等待的仿真协调流程。
- 可在无 Rhino 环境运行的声学回归断言，以及必须在 Rhino 中完成的集成验收清单。

接收器并行、池热路径重构、共享功率缓冲、几何输出容器复用和散射策略调整均不随本期自动实施。性能结果只按实测报告，不预设加速倍数。

## User Stories

1. 作为仿真用户，我希望看到每个声源的构造、追踪、滤波和总耗时，以便知道等待发生在哪里。
2. 作为批量计算用户，我希望后续声源复用已建立的对象池，以避免反复创建大量池对象。
3. 作为插件调用者，我希望并发取得池入口时得到同一个完整初始化实例，以避免读到半初始化状态。
4. 作为仿真用户，我希望重复初始化不替换已有池或破坏正在使用的射线，以保证连续计算可靠。
5. 作为大量接收点用户，我希望直方图只分配最终需要的能量数组，以减少构造期间的垃圾分配。
6. 作为八度／第三倍频程用户，我希望两种频带模式和方向数据结构都保持完整，以保证结果可用。
7. 作为滤波调用者，我希望入口返回时滤波已经完成，失败时可以捕获异常，以避免使用半成品结果。
8. 作为 Rhino 用户，我希望滤波失败后进度状态能够复位并显示失败，以免误报成功或一直显示处理中。
9. 作为多线程追踪用户，我希望三类反射数据都不丢失累加，以获得可信的反射分析。
10. 作为详细收敛模式用户，我希望检查器使用完整的累计 RAD，以按正确条件结束追踪。
11. 作为最小收敛模式用户，我希望每轮检查能看到该轮新能量，以避免因数据不可见而无法收敛。
12. 作为长时间收敛计算用户，我希望内存中不持续保留所有历史任务，以免迭代次数增加额外负担。
13. 作为取消计算的用户，我希望已有取消流程仍能结束当前工作并恢复界面，以免优化留下后台写入或失效状态。
14. 作为 Rhino 用户，我希望计算完成后尽快显示结果，而不再固定等待数秒。
15. 作为无进度反馈模式的调用者，我希望等待同样不阻塞调用线程，以便界面或其他工作继续运行。
16. 作为结果比较者，我希望优化不修改功率谱、共享频带表或声学抽样规则，以便比较前后结果。
17. 作为维护者，我希望每个修复都有可复现测试和阶段指标，以便定位回归而不是依赖主观体感。
18. 作为维护者，我希望未验证的性能猜测和已确认的问题分开记录，以便后续只投入值得做的优化。

## Implementation Decisions

### D1. 先建立分阶段基线，再评价收益

关联：审计测量章节、#1–#3、#10、UI 等待。

- 复用现有日志渠道，在 Hybrid 与 Mapping 的主要流程记录每源准备／构造、追踪、滤波、等待和端到端墙钟时间；准备／构造中标明接收器与追踪器／池成本。Mapping 的循环前构造成本须归属于相应声源或明确列为批次准备，不能遗漏。
- 用单调计时测墙钟，说明阶段边界与嵌套关系；工作时间和包含该工作的 await 总时间不可重复相加。未启用的阶段标为未执行，而不是伪造为一次零耗时运行。
- 保留原有公开计数字段的含义；明确现有子射线计数不是全部生成分支数，不能用它直接推断完整分支树或每次求交成本。本期不新增逐射线计数／日志热点。
- 计时输出是有限的每源摘要，不添加日志服务、新配置或依赖；采用现有日志开关，没有开关则沿用现有计算摘要的输出行为。
- 累计分配、可达内存、进程峰值、GC 暂停和 CPU／锁等待使用兼容当前运行时的分析工具分别采样，不以跨 await 的单线程分配统计替代全流程分配。

### D2. 对象池生命周期只解决安全创建与幂等，不扩张并发保证

关联：#1；受 #4 的租约边界约束。

- BroadRayPool 与 OctaveRayPool 各只有一个线程安全惰性创建入口，可使用标准库的一次初始化机制。Initialize 仅确保实例存在；Instance 返回同一实例；构造期间不向外发布实例。
- “线程安全”仅指 Initialize／Instance 的一次创建与发布，不是整个池的并发承诺；单个仿真实例内部仍保留现有多工作者租借，本期既不改为串行租借，也不扩大租借并发范围。
- 保留默认容量 200,000／5,000，以及现有租借、生成和归还入口签名。本期不引入重置接口，不再用 Initialize 隐式重置容量、位置、信号量或在用对象。
- 核查 SplitRayTracer、IS_Trace、声源生成和 GeometryPool 等消费者；保留它们的调用兼容性，重复 Initialize 不再要求重新建立池引用。仅写未读且失去用途的初始化标志可删除。
- 本项改变“每次重建”的生命周期行为，必须通过连续多源及冷／暖运行测试，不能称作无行为差异的一行修改。
- 不修改环形出租和匿名归还算法，不宣称池已对任意归还顺序安全，不开启多个仿真实例并发。若基线或回归暴露在用射线被再次出租，应暂停相关性能合并并报告为独立正确性阻塞，不能靠重置或加速压过问题。

### D3. 方向直方图复用基类已完成的 Energy 初始化

关联：#2。

- 两种方向直方图构造方式均只保留一份最终 Energy 数据；基类初始化、Pressure、正负三轴方向及三类 RAD 的结构和零值语义保持不变。
- 兼容 8／24 band、样本数及毫秒时长构造；结果读写格式保持不变。
- 分配验收针对少分配了一份 Energy，而不是声称稳定存活内存也下降相同数值。数组头等开销由运行时实测，不写死为精确字节承诺。

### D4. 保持串行滤波，明确同步完成和失败契约

关联：#3。

- `Receiver_Bank.Create_Filter` 的批量 void 入口保留现有公共签名和串行顺序，移除没有实际异步工作的修饰及死任务代码；本期不增加异步并行分支或新的异步入口。
- 正常返回意味着全部所需滤波已安装；发生错误则向调用方抛出原始失败，不转为后台未观察异常，不将失败标记为完成。CreatingFilter 在正常及异常退出后都复位。
- 返回滤波数组的两个重载保留原有签名与返回值语义；同样在运算结束后才返回、向调用方传播失败，并在正常／异常退出后复位 CreatingFilter，不把返回数组改成隐式安装结果。
- 逐一核查同步反序列化、结果重建、声源编辑、Hybrid 和 Mapping 等调用场景。同步调用须直接观察失败；后台执行的 UI 调用须等待其 Task，并通过现有错误展示路径报告失败、清理进度状态。不存在错误路径时在调用边界补齐，不吞异常或发布未完成结果。
- 进度反馈沿用现有 UI 调度方式，不把 Rhino／窗体操作任意搬到工作线程。保留 FFT 槽位策略和滤波算法，接收器并行不是本项验收条件。

### D5. 修复 RAD 累加，不引入线程接收器副本

关联：#8；保持 #7 描述的收敛可见性。

- 单频带 OctaveRay 的镜面、散射、散射后镜面三种类别，与现有宽带／多分量路径采用一致的每频带累加同步。累加前校验目标样本在有效范围内，窗口外样本不写入；保持现有有效样本索引规则。
- 直方图累加与 RAD 累加分别完成，不嵌套持有二者的锁；检查所有相关写入及读取边界，避免锁顺序反转。
- 保持主接收器直接累计，收敛检查仍在本轮全部任务完成后读取该银行的完整累计 Energy／RAD；不增加只在最终结束时才合并的副本。
- 固定射线数、最小收敛（负值）和详细收敛（零）分别验证。详细模式修复后可能因纠正丢更新而改变终止时机和最终 IR，此变化应明确说明，不应回退修复来迁就有竞争的旧结果。

### D6. 限定收敛任务集合的生命周期

关联：#10。

- Calculate_Conv 的任务集合仅表示当前轮，不继续持有和重复等待以前各轮的任务；当前轮任务全部结束后才能检查收敛、开始下一轮或完成退出。
- 保持每轮 Revolution_Period、随机种子输入规则、声学运算、累计结果和既有取消边界。任务失败不得被当成成功收敛，不得留下继续写接收器的未观察任务；失败路径也须结算本轮已启动工作并走现有失败清理。
- 不在本项中默认删除或重新配置每轮显式 GC。先消除历史任务引用，测量剩余 GC 成本；是否移除由独立、带内存峰值对照的后续修改决定。

### D7. 先检查仿真状态，再异步等待；调用方直接等待结果

关联：审计 UI 等待章节。

- RunSimulation 保留现有 Task 返回签名。启动后及结果合并后先检查现有状态协议，确需等待才异步延迟；两个阶段和 needfeedback 的两个取值都不使用阻塞式休眠。
- 本期保留内部正在运行时的 3,000 ms 轮询间隔，不引入新的配置或完成通知框架；已完成状态不付出首次或合并后的固定延迟。这不承诺正在运行的任务一结束便零延迟显示。
- 在正常完成路径保留一次 Combine_ThreadLocal_Results 及其顺序；合并若启动后续工作，继续按现有状态协议等待该工作。失败／取消时不在仍有写入者的情况下强行合并，保留各仿真类型的安全退出语义。
- Hybrid／Mapping 中对 RunSimulation 结果的消费者直接 await，去掉外层 GetAwaiter 加 Delay 的二次轮询；其后读取结果和启动下一阶段的顺序不变。
- 正常、取消及异常退出都保留自动保存、重绘、进程优先级等现有 finally 恢复；UI 更新保持在正确线程。本期不增加新的取消 API。

## Testing Decisions

### 测试边界与先例

主要自动化边界是现有 SplitRayTracer／Receiver_Bank 公共行为，而不是为每个私有方法增加接口。需要固定随机输入时优先使用现有可显式提供种子的 Calculate 参数入口；仅在测试无法表达所需行为时，提出一个最小的内部测试入口，不增加用户设置。直接构造接收器和检查池身份用于各自独立契约的断言。

本轮未发现受版本控制的现成测试工程或可复用测试框架。新增一个独立于生产源目录、通过项目引用访问 Universal 的轻量控制台断言工程；不依赖 Rhino、不添加测试包、不使用私有反射。它不作为生产项目的依赖，也不能被生产项目默认源文件通配规则编入；运行方式必须写清。核心断言须能在当前支持的 net7.0／net48 环境分别运行，缺少工具或 SDK 时报告阻塞，不记作通过。

测试断言外部可见的完成、失败、累计结果和数据独立性，不断言私有锁类型、字段布局或具体任务容器实现。分配／CPU 由独立测量验证，不能只靠测试通过宣称更快。

### 自动化验收矩阵

| 验收 | 必须覆盖的行为 |
|---|---|
| T1 池创建（D2） | 首次并发访问 Initialize／Instance 与反复调用得到相同、完整实例；持有射线时再次初始化不替换实例或修改该射线；全部借用配对归还；沿用既有并发量记录活跃借用的对象身份，若同一射线在归还前再次被出租，报告为独立阻塞，不在本期暗改租约算法。 |
| T2 连续计算（D2、D5） | 至少两个不同功率谱的声源依次计算，冷／暖池结果正确；先前结果不被下一声源覆盖；8／24 band 均通过。 |
| T3 直方图（D3） | 两种构造方式、两种频带数、零值及末样本、Energy／Pressure／方向结构一致；分配对照证明不再付出第二份 Energy 成本。 |
| T4 滤波契约（D4） | 批量入口正常返回时全部接收器滤波可用，返回数组的重载保持结果语义；三个入口的可控失败均可被调用者观察，批量后台调用的失败可由 await 观察；各入口正常／失败后的 CreatingFilter 均复位，失败不发布新完成结果。 |
| T5 RAD（D5） | 用可重复命中同时累加三种类别，比较单线程参考与多工作者结果；覆盖单频带及第三倍频程多分量路径、样本 0、末样本和窗口外输入。 |
| T6 固定数量追踪（D2–D6） | 固定场景、工作者数量、每工作者种子及射线区间、声源初态和射线总数后，比较修改前后的 Energy、Pressure、方向及滤波结果，保留频带选择和声学贡献；声源功率及共享频带表不被跨射线误改。 |
| T7 收敛（D5、D6） | 最小／详细两种模式分别跨越多轮，每轮检查可见上一轮累计数据；最后一轮所有贡献计入；在有有效能量且满足原收敛条件的夹具中结束。零能量／无命中用例按原规则处理，不新加“自动收敛”规则。 |
| T8 生命周期（D4、D6） | 多轮后无按轮数持续增长的历史任务保留；取消及受控任务失败不会提前宣布成功，也不遗留本轮后台写入；滤波失败不遗留处理中标志。 |

- 确定性回归在同平台、同运行时、同场景、相同工作者数量／分配和相同随机输入下运行。先证明单工作者参考可重复，再比较修改版本；多线程浮点累加使用逐元素判定：绝对差不大于 `1e-12 + 1e-9 × max(|参考值|, |结果值|)`，并拒绝新出现的 NaN／无穷值。若基线精度不支持此阈值，应报告差异及原因，不默默放宽。
- 并发计数／贡献不丢失另用可精确表示的受控输入严格断言，不能用浮点容差掩盖丢更新。RAD 对照串行正确参考，不对照旧竞争输出。
- 收敛模式不要求修复后的射线数量逐位等于旧竞争版本；要求原阈值、每轮样本规则及检查数据来源正确，记录终止轮次和射线数解释变化。
- 分配对照在池已暖、输入规模固定的条件下测量；测试夹具不得把生产全量 GC 或每轮重建对象池当成清理手段，否则会遮蔽待修复行为。

### Rhino 集成验收

- Hybrid／Mapping 分别覆盖固定数量、最小和详细收敛，以及 8／24 band；覆盖 Direct、ImageSource、IS_Trace 和 RT 中实际启用的阶段组合，不扩张各阶段内部算法。
- 已完成仿真和无后续工作的合并路径不再额外等待 3 秒；确有合并后工作时仍正确等待。needfeedback 为真／假时界面均可继续处理交互。
- 核查加载结果、重新生成滤波、编辑声源功率等所有滤波消费入口；错误能展示，进度窗口和处理标志能清理，不使用半成品结果。
- 验证正常、取消及异常退出的自动保存、重绘和优先级恢复；不得在工作者仍运行时启动下一声源或发布已完成结果。

### 性能验收与后续决策

- 固定一套公开记录参数的代表性场景，至少比较 1 个与 3 个声源，并包含足以观察接收器分配的多点场景；保持源功率、几何、接收点、时长、采样率和计算模式一致。区分冷启动与暖池，暖运行至少 3 次，报告中位数、范围和内存峰值，不只报告最快一次。
- 硬性验收是：每个池只构造一次、少分配一份 Energy、已完成路径无强制等待、历史任务不累计、声学及失败路径测试通过。没有硬件证据前不写总耗时百分比目标。
- 同时提交分阶段墙钟、分配、GC、峰值内存和可用的 CPU／等待分析。出现稳定的总耗时或峰值回归时必须解释并定位，不能用减少射线数、频带或接收点来掩盖。
- 后续优化的立项门槛：重复测量把对应机制列为可解释的显著成本，并已有可用的所有权／收敛／误差与内存验收方案。几何或 FFT 不能因已有线程局部缓存或加速结构就被排除；未达到门槛则只记录观察，不实施猜测性重构。

## Out of Scope

- 声源级并行、全局线程安全承诺、BroadRayPool 租约／归还 API 或环形算法重构。
- 不同工作者数量、不同平台／运行时之间的逐位确定性，以及为此改造随机调度。回归中的修改前后对照保持工作者数量和每工作者种子一致。
- 直接共享 SourcePower，按 threadid 复用仍可能重叠存活的功率缓冲，盲目清空共享频带／能量数组，无锁索引替换。
- 并行构建接收器滤波、改 FFT 槽位策略、异步公共 API 迁移。
- 复用会逃逸的求交输出列表，重写 Voxel／Octree／KDTree 算法。
- 接收器线程副本、末尾合并方案、接收器分块、距离量化查表。
- 散射阈值、概率抽样／俄罗斯轮盘、减少声学工作量或改变收敛判据。
- 未经测量直接移除／重新配置显式 GC，新增调参开关、依赖、缓存框架或遥测服务。
- Direct_Sound、ImageSourceData、IS_Trace 内部算法优化，结果文件格式变更，以及与本修复无关的现有用户改动。
